Write in English, use lowercase erp4us, check the application roadmap before making capability claims, and keep policies compatible with the main repository. Preview changed templates, verify links, and record the result in the PR. No changes to governance or brand selection without maintainer approval.

## Describe the outcome first

Frame proposals, intake templates and PR summaries around the person's task and decision, not a new list of records. Ask for a concrete question, evidence needed to answer it, and the next permitted step. “Why can't I build this product?” calls for a supported blocker and a link to the affected assembly or reservation, not a menu of reports. Keep examples usable without chat or AI, and do not confuse a proposed workflow, a fixture, or an open PR with a shipped capability. A helpful answer does not authorize a write.

## Dependency changes

Follow the [monthly maintenance policy](https://github.com/erp4us-org/.github/blob/main/docs/dependency-maintenance.md). Keep alerts and grouped security updates enabled, scheduled version PRs and auto-merge disabled. Preserve lockfiles and pins; review advisories, licenses, migration and rollback, and require passing gates before manual merge. Expedite critical fixes.
